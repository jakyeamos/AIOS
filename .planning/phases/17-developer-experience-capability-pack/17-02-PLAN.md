# Plan 17-02: Capability Contract, Modes, Metrics, And Second-Brain Parity

## Objective

Design the Developer Experience pack before implementation. The design must be machine-readable enough for routing and evaluation, while still clear enough for agents and humans.

## Scope

Create or extend the appropriate registry identified by Plan 17-01. If no existing registry fits, create `config/developer-experience/capability-pack.json`.

Create `docs/specs/developer-experience-pack-contract.md`.

## Required Capability Contracts

Define:

- `dx_optimizer`
- `interface_dx_reviewer`
- `docs_writer`
- `security_reviewer`
- `typescript_specialist`
- `spec_fidelity_coder`

Each contract includes:

- purpose
- responsibilities
- invoke_when triggers
- avoid_when triggers where relevant
- default mode
- supported modes
- required output schema
- evidence expectations
- assumptions policy
- second-brain behavior

## Required Metrics

Cover:

- clone to running app
- setup time
- dev server startup
- hot reload or feedback loop speed
- unit test runtime
- typecheck runtime
- lint runtime
- build runtime
- CI runtime
- manual setup steps
- validation command count
- README quickstart presence
- automated setup validation presence
- ambiguous or missing developer instructions
- token cost and agent calls when telemetry supports it

## Verification

- JSON validates as parseable structured data.
- Contract document describes all six capabilities.
- No capability hardcodes a fixed model.
- Metrics support `not_measured` with measurement method.
