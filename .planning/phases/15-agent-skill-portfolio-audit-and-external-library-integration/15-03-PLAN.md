# Plan 15-03: Add Diagnose Debugging Skill

## Objective

Create a standalone `diagnose` skill that gives agents a disciplined debugging protocol — or merge these behaviors into an existing debugging skill if the Plan 15-01 inventory found one worth extending.

## Seven Core Behaviors

### 1. Build The Feedback Loop First
Before hypothesizing, establish the fastest path to seeing the failure deterministically. This means: identify the entry point, write the minimal reproduction command or test, confirm the failure is reproducible on demand. A bug you cannot reproduce reliably cannot be fixed reliably.

### 2. Reproduce Before Hypothesizing
Run the reproduction command and confirm the failure. Only after the failure is confirmed and understood at the surface level should hypothesis generation begin.

### 3. Generate Ranked Falsifiable Hypotheses
List all plausible root causes ordered by likelihood. Each hypothesis must be falsifiable — there must be a concrete observation or test that would rule it out. Annotate each with the evidence that makes it more or less likely.

### 4. Instrument One Hypothesis At A Time
Test hypotheses in order. Make one change (add one log, flip one flag, isolate one code path). Observe the outcome. Only then move to the next hypothesis. Changing multiple variables simultaneously makes it impossible to know what fixed (or broke) what.

### 5. Write The Regression Test At The Correct Seam
Once the bug is confirmed, write a test at the level that would have caught the bug earliest. This is usually not the UI layer and not necessarily the unit layer — it is the seam where the invariant was violated. Name the test after the bug's root cause, not its symptom.

### 6. Remove Debug Artifacts
Before marking a bug fixed: remove all `console.log`, `print`, temporary flags, hardcoded overrides, and any prototype code introduced during investigation. The fix should be clean enough to review without debugging noise.

### 7. Write A Postmortem Or Commit Explanation
The commit message or a brief closing comment must name: what the root cause was, what conditions contributed to it, and what the fix does. Future readers should not need to re-investigate.

## Architecture Handoff

When the bug reveals a missing abstraction, unexpected coupling, or a seam that should exist but does not, add a note before closing:

> "This bug exposed architectural friction in [module/file]. Recommend running the `simplifier` architecture review on this area."

Do not silently close the bug when it exposes structural debt. Name the debt and point to the right next step.
