# Plan 15-04: Upgrade Simplifier Skill With Architecture-First Review Workflow

## Objective

Upgrade the local simplifier skill to add architecture-candidate thinking and a mandatory report-before-edit discipline for major refactors. The skill should not just make code shorter — it should make modules more deeply encapsulated, better seamed, and more navigable.

## Nine Architecture Lenses

Add explicit definitions of each lens so an agent can apply them without guessing:

### Deep Modules
A module is deep when it has a simple interface and rich internal behavior. Complexity is hidden behind a narrow API. The opposite of a deep module is a shallow module — a thin wrapper around its internals that leaks implementation detail into its callers.

### Shallow Modules
Flag shallow modules as candidates for either elimination (if they add no value) or deepening (if the behavior they wrap should be combined with related behavior into a single deeper module).

### Deletion Test
For any abstraction, ask: if this were deleted and callers called the underlying thing directly, would anything be worse? If not, the abstraction is not earning its complexity budget.

### Interface As Test Surface
A well-designed interface is one you can test from the outside without knowing the internals. If testing a module requires mocking its dependencies or reaching into its internals, the interface is wrong — the seam is in the wrong place.

### Seams
A seam is a place where you can swap behavior without modifying the code that uses it. Good seams make testing, extension, and future change cheap. Missing seams make all three expensive.

### Adapters
An adapter isolates a volatile external dependency (a third-party API, a database driver, a file system call) behind a stable internal interface. If the external thing changes, only the adapter changes.

### Locality
Related things should live close together. Scattered logic that must be assembled mentally before it can be understood has high locality cost. Consolidation is often the right move.

### Leverage
High-leverage code is code that is called by many callers and whose improvement improves all of them. Low-leverage code is specific, called once, and not worth abstracting. Identify the leverage ratio before investing in an abstraction.

### AI Navigability
Would a new agent reading only this module's public interface — without reading its callers or its dependencies — understand what this module does, what it guarantees, and what it expects? If not, the interface is not AI-navigable and should be improved.

## Report-First Discipline For Major Refactors

For any refactor touching more than three files or removing/moving more than 50 lines, generate a written review BEFORE editing code:

### Architecture Review Report Template

```markdown
## Architecture Review: [Area Name]

### Candidate 1: [Name]
- **Files involved:** [list]
- **Current friction:** [what is painful or confusing about the current design]
- **Proposed change:** [simplification or deepening — not necessarily deletion]
- **Expected test improvement:** [will this make tests easier to write, faster, or more meaningful?]
- **Risk:** [what could break or regress]
- **Confidence:** [high / medium / low — with rationale]
- **User approval required:** [yes if behavior changes, APIs change, or risk is medium+]

### Candidate 2: ...
```

Post the report and wait for user review before making any edits, unless confidence is high and risk is low.

## What Simplification Is Not

Simplification is NOT:
- Making files shorter
- Splitting large files into many small ones with no new encapsulation
- Removing comments or docstrings
- Renaming variables for style preference

Simplification IS:
- Reducing the number of things a caller must know to use a module
- Hiding decision logic behind a well-named function
- Removing an abstraction that adds complexity without adding clarity
- Deepening a module to eliminate repeated patterns across its callers
