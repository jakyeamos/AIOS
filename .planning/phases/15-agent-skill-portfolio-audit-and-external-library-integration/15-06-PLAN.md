# Plan 15-06: Add Prototype Skill

## Objective

Create a standalone `prototype` skill that disciplines agents to build throwaway, clearly-scoped experiments rather than accidentally building a second implementation or producing code that lingers.

## The Core Discipline: State The Question First

Before writing a single line of code, the agent must complete this sentence:

> "This prototype will answer: ___"

If the answer is vague ("see if the approach works") or describes a feature rather than an uncertainty ("build a login form"), stop and ask the user to sharpen it. A good prototype question is specific, falsifiable, and answerable within the prototype's scope:

**Good:** "Will batching these DB reads in groups of 50 reduce P95 latency below 200ms?"
**Good:** "Does this state machine correctly handle the concurrent-edit edge case?"
**Bad:** "See how React Query handles caching."
**Bad:** "Build the auth flow so we can review it."

## Prototype Type Selection

Choose the type based on the question:

| Type | When To Use |
|------|------------|
| **Logic/State prototype** | The uncertainty is about algorithm correctness, data flow, concurrency, edge cases, or computation |
| **UI prototype** | The uncertainty is about layout, interaction feel, or how a component composes visually |

Do not build both unless there are two distinct uncertainties. Name which type is being built before starting.

## Five Non-Negotiable Rules

### 1. Clearly Marked As Throwaway
Every prototype file must start with:
```
# PROTOTYPE: [question being answered]
# This file is throwaway. Do not merge. Delete or absorb after: [question]
```

Use a filename prefix like `proto_` or `prototype_` for all prototype files.

### 2. Single Command To Run
The prototype must be runnable with exactly one command:
```bash
python proto_batch_reads.py
# or
node prototype_state_machine.js
# or
npx tsx proto_ui_layout.tsx
```

If it requires setup steps, the setup must be automated into the run command or a `proto_setup.sh` script.

### 3. No Persistence By Default
- No writes to production or development databases
- No mutations to real files
- No API calls that create or modify real data
- Use in-memory fixtures, mocks, or test databases explicitly named as such

If the prototype genuinely needs a side effect to answer the question, name it explicitly and get user confirmation.

### 4. Expose Full Relevant State
After each action or step, print the full relevant internal state — not just the final result. The goal is to make the uncertainty visible:

```python
print(f"Batch 1: {len(batch_1)} items, latency={t1:.1f}ms, cache_hits={hits_1}")
print(f"Batch 2: {len(batch_2)} items, latency={t2:.1f}ms, cache_hits={hits_2}")
print(f"P95: {p95:.1f}ms — {'PASS' if p95 < 200 else 'FAIL'}")
```

### 5. Delete Or Absorb After The Question Is Answered

Once the prototype has answered its question, one of two things happens:

- **Delete:** the question is answered and the implementation approach is clear; remove all prototype files
- **Absorb:** the prototype contains logic worth keeping; extract that logic into the real implementation, removing the prototype markers

A prototype that is neither deleted nor absorbed becomes technical debt. The skill must prompt for a decision before the work session ends.

## Standards

- This skill must be standalone — it does not depend on any other skill or AIOS service.
- The description must not trigger on requests for a full feature implementation, only on uncertainty-resolution requests.
- Add a warning: prototype code must never be committed to `main` or a release branch.
