# Plan 22-01: Promote AIOS Standards Into The Commit Quality Ladder

## Objective

Turn AIOS standards from repo-local governance into a progressive commit-ladder stage that can run across the device without breaking non-AIOS repositories. Phase 22 is the fail-closed promotion phase; earlier phases may only introduce warn-only or AIOS-local checks.

## Scope

### 1. Standards coverage matrix

Create or update `docs/quality/aios-standards-ladder-contract.md` with a row for every global AIOS standard considered for hook enforcement:

- rule id
- source file
- check summary
- portability: `portable | AIOS-local | not-hook-suitable`
- evidence requirement: `staged-file | command-evidence | verifier-artifact | AIOS-state`
- current mode: `off | warn | fail`
- waiver format
- false-positive risk
- promotion blocker

### 2. Backfill across first-class projects

Run the candidate checks across AIOS and linked first-class projects in non-mutating mode. Record:

- pass/fail/warn counts
- false positives
- required waivers
- remediation candidates
- checks that must remain AIOS-local

### 3. Progressive rollout

Promote checks in this order:

1. `off` to `warn` when the check has deterministic output and actionable messages.
2. `warn` to `fail` only after the backfill report shows acceptable false-positive risk.
3. Evidence-dependent checks may fail only when Phase 16 evidence/verifier artifacts are fresh and cited.
4. AIOS-state checks stay inside `services/commit_quality_ladder.py` and must not block arbitrary repos through the global hook.

### 4. Hook implementation

Update the user-level hook and AIOS-local ladder so they share the same rule ids and output shape while preserving different enforcement scopes:

- global hook: portable staged-file checks plus Pre-CR bridge
- AIOS hook: full standards inventory, context validation, success criteria, evidence-backed standards, and truth/writeback checks

## Standards

- Default new standards to `warn` before `fail`.
- Do not require AIOS runtime state in non-AIOS repositories.
- Every fail-closed check must provide a waiver path that requires a concrete runtime or governance reason.
- Every warning promoted to failure must have backfill evidence and a false-positive note.

## Verification

- Tests cover per-check modes, waivers, and output shape.
- Tests prove AIOS-local checks do not run in arbitrary repos.
- Backfill report records candidate checks against first-class projects.
- Manual hook run succeeds in a clean repo and fails on at least one fixture violation with an actionable message.
