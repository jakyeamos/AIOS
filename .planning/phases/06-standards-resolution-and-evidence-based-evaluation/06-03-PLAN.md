<objective>
Close the remaining standards-aware execution surface: broaden execution-first verification evidence ingestion (STND-03), fix the pure-doc false-positive trigger (Pitfall 2), and expose finding-lifecycle and resolution-preview commands through the aios CLI so operators can drive STND-04 finding states.

Purpose: STND-03 currently fires on `code_changes and not test_changes` but only sees evidence from `artifacts` and `rtk_compression_events`, producing false-negative blockers when tests ran via a non-RTK path. Pitfall 2 documents a parallel false-positive where markdown-only edits under `services/` trip the core-logic marker. Plan 03 fixes both, then ships the missing lifecycle CLI so STND-04 finding states actually transition (Pitfall 5).

Output: broadened `execution_evidence_for_session` in `bin/hook-stop.py`, an extension-aware filter on `EXECUTION_FIRST_PATH_MARKERS` in `services/success_criteria.py`, two new `aios` CLI subcommands (`criteria-finding resolve` and `standards-resolution preview`), governance-audit stage-finding aggregation, and tests covering each.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI operator -> finding state | The `criteria-finding resolve` command writes operator-supplied actor + rationale to the resolution columns. Operator input must be validated (status enum) but rationale text is recorded verbatim. |
| tool_events evidence -> execution-first evaluator | tool_events rows are written only by managed hooks (`hook-post-tool-use.py`), so the evidence path cannot be forged from outside the harness. |
| standards-resolution preview -> read-only | The preview command must not mutate any persisted state — it is a pure projection of registry data. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-09 | Tampering | execution-first evidence ingestion | mitigate | tool_events are written by managed hooks only; no operator-supplied write path. workflow_execution_reports are written by the orchestration runtime. The evaluator deduplicates evidence and truncates command strings to 200 chars to bound storage. |
| T-06-10 | Repudiation | criteria-finding resolve | mitigate | The resolve command records `resolution_actor` (defaulting to "operator-cli") and a `resolved_at` timestamp on every transition; status is validated against EVALUATION_FINDING_LIFECYCLE_STATES so unknown states cannot mask outcomes. |
| T-06-11 | Information Disclosure | standards-resolution preview | accept | The preview command exposes registry + project-profile data the operator already has read access to; no secrets are touched. |
| T-06-12 | Elevation of Privilege | finding lifecycle waiver | mitigate | The `--status waived` transition is allowed but the waiver_policy on the underlying standard already requires `max_days` and review_date elsewhere (phase 5 invariant). Future enforcement of waiver_policy lives in a follow-up task; this plan does not silently waive without rationale (--rationale is documented as required for waived in CLI help text). |
| T-06-13 | Denial of Service | governance-audit stage_findings query | accept | The aggregate query uses indexed columns (`resolution_status`, `level`); `recent` list is bounded to 5 rows. |
</threat_model>
