# Plan 14-03: Root Quality Gate Documentation

## Objective

Create `docs/quality/complexity-simplification-gate.md` — the authoritative specification that explains why the gate exists, when it runs, what agents must check, how to use available tools, how to record findings, and how to decide fix-now vs. defer. This is the doc that all rules, backfill docs, and project agent instructions point to.

## Scope

Create `docs/quality/complexity-simplification-gate.md` with the following nine sections:

### 1. Why This Gate Exists
Complexity compounds. A nested loop added today is a regression waiting to happen. Code that is hard to read is code that agents and humans will misread, patch incorrectly, or duplicate. The gate treats complexity and simplification as standard quality dimensions alongside tests and types — not optional cleanup after "real" work is done.

### 2. When The Gate Runs
List the 10 trigger conditions from Rule 10 verbatim. The gate runs after work completes, before the work is considered done.

### 3. What Agents Must Check
Full Gate A (Complexity/Performance) and Gate B (Simplification/Maintainability) item lists — identical to Rule 10 so the gate doc is self-contained without requiring agent-rules context.

### 4. How To Run The Gate
- Manual checklist: walk Gate A and Gate B for each changed file.
- Script reference: `pnpm quality:eval` (calls `scripts/quality-eval.sh`) for file-level size/dead-code/import-violation metrics.
- Pattern checklist: `docs/quality/complexity-checklist.md` for algorithmic patterns.

### 5. How To Write Backfill Findings
Document the hotspot template:
```
### Hotspot: <short name>
- File(s):
- Category: complexity | simplification | test gap | architecture | render performance | query/data access
- Severity: low | medium | high
- Confidence: low | medium | high
- Current issue:
- Why it matters:
- Suggested remediation:
- Behavior risk:
- Tests/benchmarks needed:
- Agent-safe?: yes / no / partial
```

### 6. Fix Now vs. Defer
Fix immediately only when: fix is under 5 lines, carries no behavior risk, and requires no test changes. Defer everything else. A deferred finding in a backfill doc is not a failure — it is evidence that the gate ran honestly.

### 7. Commit Ladder Integration

Document how the gate enters the commit quality ladder:

- After Phase 14, ladder integration is warn-only/reporting for portable checks.
- After Phase 16, AIOS-managed repositories may opt into evidence-backed blocking checks.
- After Phase 22, the global user-level ladder may promote eligible AIOS standards to fail-closed.
- Checks that require AIOS SQLite state, context receipts, or project truth updates remain AIOS-local until Phase 22 backfill proves they are portable.

### 8. Connection to AIOS Quality Standards
Findings feed into Phase 6/7 delta scoring and health infrastructure once available. The Quality Ladder in `~/.claude/CLAUDE.md` lists this as Step 5 (Hard gate after large work).

### 9. Definition of Done
Gate is complete when:
- Every Gate A and Gate B item was considered for changed files.
- All findings are recorded in a backfill doc or inline comment.
- Each finding has a fix-vs-defer decision.
- Verification commands (tests, lint, typecheck, build) were run or limitation documented.
- Commit-ladder eligibility for each check is recorded as `off`, `warn`, or `fail-eligible-later`.

## Standards

- Write this doc for agents as the primary reader, not just humans.
- Every section should be actionable, not aspirational.
- Cross-references must use relative paths from the AIOS repo root.
