# Plan 14-01: Agent Rule and Workflow Gate Addition

## 2026-06-23 Baseline Update

AIOS now has first-class success criteria for the broader quality-gate stack in `config/success-criteria/registry.json` and `spec/success-criteria/`. Phase 14 should no longer define quality gates only as prose. Its remaining job is to connect the already-landed criteria to agent instructions, the quality docs, and the standards ladder contract.

When writing Rule 12 and the ladder contract, use these existing criterion ids as the canonical names where relevant:

- `complexity-budget`
- `architecture-boundary`
- `simplicity`
- `test-quality`
- `agent-claim-verification`
- `performance-budget`
- `thin-display`
- `data-integrity`
- `api-contract`
- `supply-chain-review`

## Objective

Add the Complexity + Simplification Gate as a mandatory agent rule across the three root agent instruction surfaces: `config/agent-rules.md`, `AGENTS.md`, and `../.claude/CLAUDE.md`. Keep always-loaded text thin: root agent files should carry the trigger and pointer, while intent-specific detail belongs in quality docs and workflow packets.

This plan also creates the first AIOS standards ladder contract. Phase 14 is responsible for making the checks concrete enough to enter the commit ladder in warn-only/reporting mode, not for making them fail-closed across every repository.

## Scope

### 1. config/agent-rules.md — Rules 11 and 12

Add Rule 11 after the existing highest-numbered rule. The rule must require every future agent-file edit to decide whether the new instruction belongs in always-loaded context or should be an intent-specific pointer.

Add Rule 12 for the Complexity + Simplification Gate. The rule must define:

**Trigger:** Large piece of work defined as any of:
- Changes touching 5+ files
- Changes adding/removing 300+ lines
- New feature implementation
- Cross-package or cross-layer change
- Database/schema/query change
- Data pipeline, analytics, scoring, or model logic change
- UI surface with meaningful state/rendering logic
- Agent/workflow/orchestration change
- Performance-sensitive code path
- Code that will likely be reused as infrastructure

Keep the full checklist out of always-loaded agent files. Rule 12 should name these review areas and point to `docs/quality/complexity-simplification-gate.md` for the full triggered checklist:

**Gate Part A — Complexity/Performance Review:**
- Nested loops over growing collections
- Repeated array scans/find/filter/map inside loops
- Repeated object construction in hot paths
- Sort-inside-loop patterns
- Avoidable O(n²) joins that should use maps/sets/indexes
- N+1 database or API calls
- Render recomputation, missing memoization, unstable props, expensive client-side derived data
- Unbounded loops, repeated parsing/serialization, unnecessary deep cloning
- Data structures that should be Map/Set instead of arrays

**Gate Part B — Simplification/Maintainability Review:**
- Reduce nesting and branch complexity
- Remove duplicated logic
- Extract helpers only when clarity improves
- Improve names where intent is unclear
- Consolidate scattered logic into appropriate modules
- Delete dead code and unnecessary abstractions
- Prefer direct code over clever code
- Preserve behavior; preserve public APIs unless explicitly approved
- Follow local project conventions
- Add or update tests when simplifying logic

**Gate Part C — Verification:**
- Run relevant tests, typecheck, lint, and build
- If commands cannot run, document why

**Record-before-fix policy:** Every finding must be recorded with file, category, severity, confidence, suggested remediation, behavior risk, tests/benchmarks needed, and agent-safe classification before any fix attempt. Fixes are permitted only for findings under 5 lines with no behavior risk — all others must be recorded and deferred.

### 2. AGENTS.md — new gate section

Add a section after existing quality/standards sections:

```
## Complexity + Simplification Gate

After any large piece of work (see Rule 12 in config/agent-rules.md for trigger list), run:
- Gate A: complexity/performance review
- Gate B: simplification/maintainability review
- Gate C: verification (tests, lint, typecheck, build — or document why unavailable)

Report before fixing. Record every hotspot in a structured finding before touching any code.
See docs/quality/complexity-simplification-gate.md for the full checklist.
```

### 3. ../.claude/CLAUDE.md — Quality Ladder extension

Run complexity/performance review (nested loops, N+1, O(n²), memoization gaps) and simplification review (nesting, duplication, naming, dead code). Record findings before fixing. |

### 4. docs/quality/aios-standards-ladder-contract.md — warn-only ladder contract

Create the initial contract for adding AIOS standards to the commit quality ladder:

- Include a coverage section for the already-landed success-criteria quality gates from `config/success-criteria/registry.json`.
- Mark the success-criteria gates as AIOS-local/runtime criteria unless a separate portable staged-file check exists.
- Eligible now: cheap syntactic and staged-file checks that do not require AIOS runtime state.
- Warn-only after Phase 14: AIOS code-quality and simplification standards that can produce deterministic findings but do not yet have Phase 16 evidence binding.
- AIOS-local only: checks that require SQLite state, context receipts, success-criteria evaluation records, or project truth writebacks.
- Fail-closed prerequisites: Phase 16 evidence/verifier gates and Phase 22 progressive governance rollout.
- Waiver contract: waivers must include a named rule, concrete runtime reason, owner, and expiration or backfill reference.
- Output contract: ladder findings must identify file, rule id, severity, blocking mode (`off | warn | fail`), evidence source, and remediation.

## Standards

- Read the full current content of each file before editing.
- Add rules/sections — do not remove or restructure existing content.
- The rule text must be specific enough for an agent to apply without reading a secondary doc.
- The ladder contract must distinguish "eligible for warning now" from "eligible for fail-closed enforcement later."
