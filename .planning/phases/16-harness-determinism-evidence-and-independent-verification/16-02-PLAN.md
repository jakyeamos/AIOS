# Plan 16-02: Evidence Chain Hardening

## Objective

Bind harness completion to durable, hard-to-fake evidence. AIOS should be able to answer what command ran, where the raw output lives, what hash proves the output, which run/session it belongs to, and whether it passed, failed, or remains unknown.

## Scope

Implement the smallest additive evidence layer that fits the current harness after Plan 16-01 identifies the exact seams.

Preferred target shape:

- `services/evidence_artifacts.py` for schema, validation, and helper functions
- additive table in `schema.sql` unless an existing artifact table can satisfy the schema without ambiguity
- hook integration in `bin/hook-post-tool-use.py` and `bin/hook-stop.py`
- CLI inspection in `services/aios_cli.py`
- focused tests with temporary SQLite databases and fixture output files

## Evidence Artifact Fields

Required fields:

- `evidence_id`
- `task_id`
- `run_id`
- `phase`
- `timestamp`
- `agent`
- `model`
- `command`
- `exit_code`
- `stdout_path`
- `stderr_path`
- `output_hash`
- `parsed_summary`
- `diff_hash`
- `commit_hash`
- `status`
- `caveats_json`

## Standards

- Reuse existing run/session/artifact identifiers where they exist.
- Keep evidence additive; do not break existing hook-stop behavior for sessions without commands.
- Do not fabricate command output or pass/fail status.
- Treat missing, stale, or unhashable evidence as `unknown` with caveats.
- No heavyweight dependencies.

## Verification

- Add tests for evidence recording, output hashing, stale evidence rejection, and empty marker rejection.
- Run relevant Python checks for touched modules.
- Manually inspect at least one recorded fixture evidence row through the new CLI path.
