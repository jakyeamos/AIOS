# Plan 16-04: Context Routing Manifest And Second-Brain Parity

## Objective

Make context routing explicit, inspectable, and portable. AIOS should record what context was loaded, what was skipped, why each decision was made, whether the second brain was available, and what fallback path was used when it was not.

## Scope

Patch the existing context compiler and session-start path rather than creating a separate retrieval system.

The manifest can be persisted in the existing receipt structure, a new JSON artifact, SQLite, or a combination, depending on what Plan 16-01 finds. The key requirement is that the data is structured and testable.

## Required Manifest Fields

- `task_id`
- `run_id`
- `phase`
- `context_sources_loaded`
- `context_sources_skipped`
- `second_brain_available`
- `second_brain_used`
- `fallback_used`
- `retrieval_reasons`
- `estimated_context_tokens`
- `notes`

## Standards

- Do not require peers to have the user's second brain.
- Do not dump all context to satisfy the manifest.
- Keep stable project/rule context separate from volatile run notes.
- Preserve existing context receipts and compiled packet behavior unless replacing them with tested equivalent output.

## Verification

- Tests cover second-brain available and unavailable modes.
- Tests prove loaded and skipped context include reasons.
- Tests prove manifest output is deterministic enough to compare across ablation runs.
