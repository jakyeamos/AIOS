## Intent

Prevent dependency, lockfile, build, and package-manager changes from making a project more fragile or exposed.

## Applies When

Tasks that add, remove, upgrade, or reconfigure dependencies, package manifests, lockfiles, build tooling, install scripts, CI package installation, or deployment packaging.

## Required Checks

- Identify every new or changed direct dependency.
- Confirm the dependency is necessary and maintained.
- Check license acceptability for the project.
- Check whether postinstall or generated build scripts run.
- Confirm lockfile changes are clean and produced by the project package manager.
- Check for known vulnerabilities in the affected dependency surface.

## Blockers

- New dependency is unnecessary for the task or replaces a simple local implementation.
- Package manager drift is introduced.
- Lockfile changes are missing, stale, or generated by the wrong tool.
- Dependency adds known high-risk install, build, or license behavior without explicit approval.

## Warnings

- Dependency maintenance posture is unclear.
- Transitive risk could not be checked.
- Build/deploy impact is plausible but unmeasured.

## Evidence To Provide

- Dependencies added, removed, or upgraded.
- Reason accepted or rejected.
- Package manager and lockfile evidence.
- Vulnerability and license findings.
- Residual risk level.

## Related Criteria

- `security-review`
- `simplicity`

## Example Good

A UI library upgrade includes a clean `pnpm` lockfile diff, known-license check, and a short reason why the existing dependency is still justified.

## Example Bad

A task adds a broad framework dependency to avoid writing a small helper and commits an npm-generated lockfile in a pnpm project.
